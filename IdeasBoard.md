## New Features
- **Use a template's initial prompt for in-app launches**: The `+ New session` popover ignores `initialPrompt` today (API launches only — the field is labelled as such). For a template with no params it could run the prompt directly; with params the name prompt would also ask for the values, validated with the same regex + max length the API uses. Decide whether the prompt is opt-in per launch. `pending_review` `medium_effort`
- **Bound terminal memory across projects**: With Projects, kept-alive xterms pile up across every project the user visits. Two ideas to bound it, not needed for the first Projects release: (a) keep the PTY + its output in main but dispose the hidden project's xterm instances on switch and re-attach/replay on switch back; (b) keep today's kept-alive behaviour but cap the number of live xterms app-wide and dispose the oldest hidden one. Both need a scrollback/replay path that does not exist yet. `pending_review` `medium_effort`
- **Favorites for the New session popover**: Let the user mark templates as favorites so they sort to the top of the `+ New session` popover instead of the flat saved order. Came out of the Workspaces brainstorm: a workspace-level "default template" was rejected because ordering the popover is a favorites concern, not a workspace one. Decide whether favorites are global or workspace-scoped, and whether shortcuts/workspaces get them too. `pending_review` `medium_effort`
- **Sort the board**: A `Sort` button in the board filter bar's controls row, beside Search and `Filter` (it was in the toolbar mockup). Lets the operator pick the card order inside each column — today it is fixed (`sortByEnteredColumn`). Decide the sort keys (time in column, name, launch time…), whether the rail follows it, and whether the choice persists. `pending_review` `medium_effort`
- **A ⋯ menu in the board filter bar**: The toolbar mockup ends in a `⋯` button after Sort. No rows are defined yet; decide what belongs there, and what stays in the header ☰ menu, before building it (a control with nothing behind it is not rendered). `pending_review` `low_effort`
- **More filter types (folder, …)**: The board search matches the card NAME only, on purpose; folder and the other card fields belong to filter TYPES in the chip row. The second type brings the `+ Add filter` type step (`Tag ▸`, `Folder ▸`) that design.md defers until then, and likely more than one filter at a time (the number on the `Filter` button). `pending_review` `medium_effort`
- **Instant name sync from claude's session records**: `~/.claude/sessions/<pid>.json` carries `name` / `nameSource` and updates within ~1 s of a hook push or `/rename`, and survives `/clear`. A watcher on that directory would rename the card at once instead of on the next prompt, and would rebind a `/clear` without waiting for a hook. Investigated 2026-09-18 (probe on claude 2.1.276); deferred in favour of keeping the next-prompt design and making it visible. Fallback stays the `UserPromptSubmit` read-back. `pending_review` `medium_effort`
- **Live theme reload while authoring**: A watcher on `<userData>/themes/<chosen id>/` that re-applies the theme on save, so an author sees each edit without pressing `Reload themes`. Rejected for v1 (spec 2026-09-20 D-3: rescan + button). Decide debounce, what happens on a half-written file (the loader already fails closed), and whether the watcher runs only while Settings is open. `pending_review` `low_effort`
- **`scan()` reads every theme in full, synchronously, on main's event loop**: Since the final review, `scan()` validates the whole package rather than just the manifest, so a theme's CSS and assets are read on every scan. Bounded by the existing caps (64 KB manifest, 1 MB CSS, 5 MB assets per theme) but worst case is roughly 6 MB per theme, so ~20 installed themes is ~120 MB of synchronous I/O. It runs only on app start, on Settings open and on Reload — never a hot path — so it was accepted rather than fixed. A future fix would validate the CSS and assets without fully inlining them during a scan, or move the scan off the synchronous path. `pending_review` `medium_effort`
- **Per-workspace themes**: Considered and explicitly out of scope for custom themes v1 — the operator did not ask for it. Noted here so it is not re-proposed without knowing it was already declined. `pending_review` `low_effort`
- **A theme marketplace / installer**: Considered and explicitly out of scope for custom themes v1 — the operator did not ask for it. Noted here so it is not re-proposed without knowing it was already declined. `pending_review` `low_effort`
- **Custom hook port, and the banner suggests it**: The hook ingest listens on a fixed port (9279, 19279 dev, 29279 drive). When another program holds it, the server-health banner (UX-05) says session status is off and the only fix it offers is closing that program. Let the operator pick the hook port in Settings (like `apiPort`), and have the `port_in_use` banner suggest changing it. A new port must reach the hook settings file handed to each spawn (`--settings`); sessions started before the change keep POSTing to the old port, so decide whether they are re-launched, left without status, or the old port stays bound until they end. The drive/e2e harness POSTs to fixed ports and would need the value too. `pending_review` `medium_effort`
- **Action feedback polish (focus, motion, keyboard, disabled reasons)**: Left out of the action-feedback spec on purpose (`docs/superpowers/specs/2026-09-29-action-feedback-design.md`, Scope → Out). Focus return when a dialog closes; initial focus in Shortcuts and Settings; enter/exit motion on dialogs and menus; keyboard access to the terminal context menu; the StartingBanner popup's Escape and outside-click; the stale TagPicker copy ("the tag filter's Manage tags…"); disabled buttons that give no reason (name prompt, Tags, Workspaces); Rules' broken-marker reason visible only in a `title`. Toasts are Tab-reachable from inside a dialog (there is no focus trap — inert is the trap); the focus work inherits that knowingly. `pending_review` `medium_effort`

## Bugs
***
- **Workspace switch-back should return to the last FOCUSED terminal, not the last LAUNCHED one**: `focusWorkspace` (boardStore) re-points the pin at the workspace's most recently launched terminal. Reachable today by rail-clicking back to an older terminal after a second launch, and now more likely: an API create registers a terminal without focusing it, so leaving the workspace and coming back lands the operator in the API terminal they never opened instead of the one they were typing in. Track the last focused terminal per workspace and prefer it; fall back to most-recently-launched only when none. `pending_review` `low_effort`
- **The app header can be squeezed below `--topbar-height`**: `.app` (`App.module.css`) is a `flex-direction: column` container at `height: 100vh`, and `.header` sets neither `flex-shrink: 0` nor a `min-height` — so under content pressure it shrinks. The rail's own header pins `height: var(--topbar-height)` (`AttentionRail.module.css`), and the comment there says this header and the focused view's Board bar are deliberately the same height, so a squeezed app header breaks that alignment. Found while reworking the rail's wall (2026-09-20); pre-existing and unrelated to themes. Likely a one-line `flex-shrink: 0`, but check what actually applies the pressure before pinning a height. `pending_review` `low_effort`
