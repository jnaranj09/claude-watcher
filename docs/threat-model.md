# Threat model

Every way claude-watcher can be attacked or lose data, and the check that covers each one. A scan
nobody mapped to a threat is noise; a threat with no check is a gap you can see.
`.claude/rules/security.md` says when a row is added. Guard `tests/main/threatModel.guard.test.ts`
fails when a reference does not resolve.

## Blocking policy

- **CVE scanners** (Trivy fs on `package-lock.json`, `npm run security`): high or critical **with a
  fixed version** blocks. Medium and low are not reported. An advisory with no fix never blocks
  (nothing can be done about it).
- **Every other tool** (gitleaks, Semgrep, the guards): every finding blocks unless it is on the
  allow-list. zizmor blocks from **medium** up; its low and informational findings are not shown.
- **The default answer to a finding is a code change.** A new entry in `security/allow.json` or a
  later expiry needs the owner's agreement, written in the commit message (reason, expiry at most
  180 days ahead, narrowest id). gitleaks false positives go in `.gitleaksignore` by fingerprint,
  each with its reason.
- **A check that could not run is red** (`security/run.mjs`: docker or an image missing, a tool
  error, zero commits, files or workflows scanned, a lockfile missing from Trivy's report).
- The app ships no container image and is not deployed, so there is no image scan and no live scan.

## Where each check runs

`npm run security` runs the scanners locally (Docker needed); the CI job `ci.yml` → `security` runs
the same command on every push and PR, and `release.yml` calls `ci.yml`, so a release never skips
it. The guards, the header test and the fuzz seeds run in `npm test` (gate job). The CI job `dast`
runs the ZAP scan (`tests/e2e/dast.e2e.ts`). `weekly.yml` re-runs `npm run security` and the long
fuzz run. The release job checks the tag is on `main`, writes the SBOM and signs.

## GitHub settings (manual)

Applied by the owner after the first green CI run (a ruleset needs the job names to exist), from
the repo folder (`gh` fills in `{owner}/{repo}`). Re-check after any change to the settings or to
a required job's name: a renamed required check blocks every pull request.

```sh
gh api -X POST 'repos/{owner}/{repo}/rulesets' --input security/github/main-ruleset.json
gh api -X POST 'repos/{owner}/{repo}/rulesets' --input security/github/tag-ruleset.json
gh api 'repos/{owner}/{repo}/rulesets' --jq '.[] | [.id, .name, .enforcement] | @tsv'
```

- `main`: no deletion, no force-push, changes through a pull request, and the CI jobs `gate`,
  `security` and `dast` must pass.
- `release tags` (`v*`): only a repository admin creates, moves or deletes one.
